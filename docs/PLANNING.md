# PLANNING.md

复杂功能（>3 文件改动 或 新增公共接口）进入本阶段。简单任务直接走 `LOOP.md` 最小模式，无需产出四文档。

第一性原理：不假设用户完全清楚自己想要什么。动机/目标不清晰 → 停下来讨论；路径非最短 → 建议更好的办法。需求模糊、边界不清、异常未定义时先提问澄清，再统一产出文档。

## 四文档结构

目录：`docs/current-plan/{功能短名称}/`

| 文件 | 行数上限 | 核心定位 | 禁止写入 |
|------|----------|----------|----------|
| `spec.md` | ≤30 | 背景、目标用户、核心能力清单（一句一条）、Out of Scope、完成标准 | 函数名/参数/行号/SDK 类型/实现细节 |
| `tasks.md` | ≤30 | 任务时序清单，每条含：描述、影响文件、依赖、参考定位 | 进度状态（移到 progress.md） |
| `checklist.md` | ≤30 | 可观测、可复现、可勾选的客观验收项；补全 spec 舍弃的默认值/阈值/错误提示 | 模糊表述（"功能完整"/"运行正常"） |
| `progress.md` | ≤15 | 会话恢复字段（见下） | 任务定义、验收项 |

> **契约约束**：`spec.md` + `checklist.md` 是 Executor 与 Tester 的共同输入契约。契约模糊 = Tester 无法独立判定 = harness 失效。执行中发现契约缺陷 → 回本阶段修订，Executor/Tester 不得擅自改契约。

## 任务粒度

- 每条任务 = **单个可独立验证的功能点**，单次专注会话可完成。
- 任务总量 5~15 条。
- **不再强制**「接入主流程」「端到端验证」两条固定尾巴任务 —— 它们本质属于 checklist，不应作为独立任务占位。

## progress.md 格式

```markdown
# Progress — {功能名}

- **当前任务**: 第 N 条 — {任务描述} / (无，全部完成)
- **状态**: 🔄 进行中 / ⏸ 暂停 / ✅ 全部完成 / 🚫 阻塞
- **已完成**: N / 总数（如 3/7）
- **上次操作**: YYYY-MM-DDTHH:mm — {简要描述}
- **阻塞原因**: (无 / {具体原因})
```

每次 Phase 边界更新此文件。会话恢复时只读 `progress.md` 一个文件即可知道断点。
