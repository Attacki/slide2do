# NOTE.md — 知识笔记维护规范

`note.md` 是目录级「知识索引」，记录「这个目录为什么存在、里面有什么、谁依赖它」，帮 agent 进入目录时快速建立心智模型，无需通读每个源文件。

## 1. 存放规则（叶节点裁剪）

对于目录 X 的每个子项：
- **源文件 / 空桩文件** → 直接写入 X 的 `note.md`
- **叶级子目录**（内部无更深子目录）→ 其文件条目直接写入 X 的 `note.md`（用 `### 子目录 Y/` 小节区分）
- **非叶级子目录** → 维护自己的 `note.md`，X 的 `note.md` 仅一行指针 `→ Y/note.md`，**不展开内容**

> 核心原则：有更深子目录的子目录维护自己的 note.md；叶级内容直接写入父级。避免重复维护，避免文件爆炸。

## 2. 触发条件

新建/编辑/删除文件后，按第 1 节规则定位目标目录：无 `note.md` 则新建并初始化；已存在则**增量更新**只动本次涉及的条目，不重写整篇。

## 3. note.md 格式

```
# notes for `<从项目根目录起的相对路径>`
> 最后更新: YYYY-MM-DD — 简述本次变更

## 文件索引
### `文件名.ts`
- **用途**: 一句话说明该文件的存在理由（为什么有，非复述代码做什么）
- **关键导出**: 类名/函数名/类型名（不写行号）
- **关键方法**: （仅大型类）核心公开方法名 + 一句话作用
- **依赖**: 该文件 import 的关键项目内模块（跨包用 `@wuzi/xxx`）
- **消费者**: 哪些文件 import 它（判断修改影响面）
- **注意**: 陷阱/边界/非显然行为（无则不写）

## 子目录（各有独立笔记）
- `subdir/` → `subdir/note.md`
```

## 4. 填写原则

1. 写「为什么」而非「做什么」—— 用途说明存在理由与设计意图，不复述代码逻辑
2. **不写行号** —— 行号随代码变化频繁失效，用符号名定位
3. 依赖与消费者双向记录 —— 构成轻量级可读依赖图
4. 「注意」宁缺毋滥 —— 没陷阱就不写，禁止编造
5. 子目录仅一行指针 —— 父级不展开子目录内容
6. 空桩诚实标注 `（空 / 待实现）`，不虚构用途
7. **只写稳定的设计意图，不写单次任务实现理由** —— 判据：内容下次任务就过期 → 不写；半年后仍成立 → 才写。单次改动理由属于 Executor 自验收说明，不混入 note.md
8. **不记录测试相关内容** —— `tests/` 目录、`*.test.ts` 文件、测试用例、测试辅助代码一律不出现在 note.md 的文件索引、子目录指针、依赖/消费者字段中。测试由 Tester 独立维护，不属于业务知识图谱。

## 5. 读取策略（按需加载，禁止全量预读）

- 进入新目录工作 → 先读该目录 `note.md` 建立心智模型，再精读源文件
- 跨包引用 `import '@wuzi/xxx'` → 读对应包 `note.md` 了解导出结构
- 评估修改影响面 → 读「消费者」字段判断联动范围
- 不读：任务不涉及的目录不预读；已读且未变更不重复读；父级中的子目录指针不展开

## 6. 反模式

- ❌ 复制粘贴代码内容到 note.md
- ❌ 记录行号 / 无用元数据（行数、作者）
- ❌ 写长篇实现细节（那是代码的职责）
- ❌ 不相关目录的文件混写到同一 note.md
- ❌ 给非叶级子目录既写指针又展开内容（重复维护）
- ❌ 在 note.md 中记录 `tests/` 目录或 `*.test.ts` 文件（测试由 Tester 维护，不属于业务知识图谱）
