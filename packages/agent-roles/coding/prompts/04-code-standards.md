# 代码规范

## 通用
- 遵循现有代码库的风格（缩进、引号、分号、命名约定），不引入与新风格冲突的格式。
- 新增类型放 `@wuzi/types`；新增工具放 `@wuzi/tools`；新增 Provider 放 `@wuzi/core` 的 `provider/`；不知道放哪先查对应包的 `note.md`。
- 不创建非必要的文件；优先编辑现有文件而非新建。
- 不主动添加 docstring、注释、类型注解到未改动的代码；仅在逻辑非显然、设计取舍、边界条件处加注释。

## TypeScript / Bun
- 使用 ESM 模块规范（`"type": "module"`），import 路径带 `.ts` 后缀（Bun 直接运行源码）。
- 类型定义与实现分离，跨包共享类型放 `packages/agent-types/`。
- 禁止 `any`，必要时用 `unknown` + 类型守卫。
- 异步操作用 `async/await`，避免 Promise 链嵌套。

## 错误处理
- 仅在系统边界（用户输入、外部 API、文件 IO）做校验与异常捕获，内部代码信任类型契约不重复校验。
- 不吞异常：捕获后要么处理、要么向上抛出、要么转为结构化失败结果（如 `failResult`），禁止空 catch。
- 不为不可能发生的场景添加防御性代码（如对内部已保证非空的变量再判空）。

## 测试
- 可抽离的工具函数和类必须配套独立单元测试，放对应包的 `tests/` 目录。
- 测试不依赖网络/外部服务，provider 等 IO 走 mock。
- 一个行为一个用例，断言明确（`expect(x).toBe(y)`），避免 `toBeTruthy()` 等弱断言。

## 提交规范
- 格式：`type(scope): 摘要`（英文，摘要 ≤72 字符）。
- 类型：`feat` / `fix` / `refactor` / `test` / `docs` / `chore`。
- 仅暂存本次任务涉及的文件，无关修改拆分至不同提交。
- 不主动 commit，除非用户明确要求。
